# execute-gym-rep

Drive a single agent-gym task (a "rep") with the user as domain owner and you as the builder. Every rep runs the **same loop**: resolve the task, map its graded outcomes to the topic's atoms, draft atoms for the capabilities that have none, propose the plan, run it, validate. The task is done only when validation exits 0.

The gym exists to build the wiki, so the run is also a listening exercise — and it listens for two things, not one. **What you learned about how the surface works** is the primary output: for a proven capability that means deviations from its atom; for a gap it means the draft atom your run just tested. **Where the guidance failed you** is the secondary output: corrections to pages and atoms that already exist. The first fills the wiki; the second fixes it. A rep that hits no problems still produces a report — smooth is not empty.

## Run telemetry (required — every rep, first and last act)

Every rep writes a timing trail to the append-only ledger `0_admin/logs/gym-run-log.jsonl` via `rep_log.py` (bundled here). It is one cheap call per phase boundary and it is what makes "where did the time go" a measurement instead of a guess — a roughly one-minute-of-agent-time-per-rep target is asserted against this ledger, per rep and as a trend.

```
python .claude/skills/execute-gym-rep/rep_log.py AG-LAK-006 start          # before step 1
python .claude/skills/execute-gym-rep/rep_log.py AG-LAK-006 phase classify # at each transition
python .claude/skills/execute-gym-rep/rep_log.py AG-LAK-006 note "waiting on graph refresh"
python .claude/skills/execute-gym-rep/rep_log.py AG-LAK-006 end --status passed
python .claude/skills/execute-gym-rep/rep_log.py AG-LAK-006 report         # quote this when you debrief
```

Canonical phase names, matching the loop below: `resolve` · `preflight` · `classify` · `draft` · `plan` · `payload` · `engine` · `build` (hand-orchestrated topics) · `triage` · `debrief` · `report`. Mark a phase when you *enter* it; `end` closes the last one — after the tracker refresh, with `--status passed|failed|parked`. The validator (`gym_validate.py`) logs its own live runs into the same ledger automatically, so every triage re-run is captured with no extra calls; the engine (`gym_run.py`) does **not** auto-log — its fabric-vs-local split lives in its printed telemetry summary and the gym rep report (`rep_log.log_engine` exists for manual or future wiring). Cross-run trend: `python .claude/skills/execute-gym-rep/rep_log.py --summary --last 20`.

## Task ids

`AG-<TOPIC>-<NNN>` — `AG` = agent-gym, `<TOPIC>` = a three-letter topic code, `<NNN>` = the zero-padded task number.

- `ONT` → `1_agent-gym/ontology/` (the Fabric IQ ontology gym). `OMR` → `1_agent-gym/openmirror/` (the Open Mirroring gym). Others (`GRA` graph, …) plug in as topics gain gyms; the code→folder map lives in `gym_validate.py` (`TOPIC_DIRS`).
- Example: `AG-ONT-001` → `1_agent-gym/ontology/AG-ONT-001/`. The task folder is named by its canonical id.

If the user gives a bare number or a name, resolve it against `1_agent-gym/ontology/index.md` and confirm the id before starting.

## Where the answers live (and where they don't)

The curated wiki is the source of truth for solving any rep, whatever the topic. Read from the wiki and only the wiki:

1. **The atoms of EVERY topic whose items the task builds — `3_wiki/<topic>/atoms/`** — the execution cards, one per rep-proven capability: the proven call shape plus the gotchas that bite. Start here. **"The topic" means the item types you are about to create, not the folder the task lives in.** A data-agent task that stands up an ontology is an ontology build as much as a data-agent one, and the ontology topic's atoms are required reading before the first call — not after it fails: an atom documenting a naming rule saves the rep that would otherwise die on `400 BadArtifactCreateRequest`. Reading it costs a minute; not reading it costs the run. In a fresh clone every `atoms/` folder is empty — then the classify step's output is pure gaps, and drafting the missing atoms IS the rep's research.
2. **The topic's wiki folder — `3_wiki/<topic>/`** — the curated cluster pages, canonical for reasoning; escalate here when an atom isn't enough or a capability has no atom, plus any closely-related topic folder the task leans on (an ontology task that queries its graph also reads the graph topic's folder). The `task.md` links the specific pages it depends on.
3. **The toolkit — `code/`** — the proven, runnable clients a rep builds with, when the topic has them. Start from its `README.md`, which maps each module to what it does.

**Do not read `2_raw/gym-rep-reports/` reports (or anything else in `2_raw/`) to solve a task.** Those are immutable provenance — every finding in them has already been folded into the wiki pages above, which are the curated, current version. Reading them re-introduces stale, un-distilled detail and duplicates what the wiki already says. `2_raw/` is a *write* target at the end of a rep (the gym rep report you produce), never a *read* source during one. The only reason to open a gym rep report is a deliberate audit of the wiki's provenance — not building. This includes formatting: the shape of the gym rep report you write comes from `0_admin/references/gym-rep-report-template.md`, **never** from opening a prior report to copy its structure.

## The loop — every rep, same protocol

Three plain words: the **task** (`task.md` + `provision.py` + `validate.json`), the **plan** (the typed step list you propose and pass via `--plan`), and the **payload** (the solution code a step consumes via `--payload` — for lakehouse, the notebook body).

There is no task-level mode. The proven/unproven distinction is **per capability**, decided at rep time by the atom index: a capability with an atom is executed from it; a capability without one is a **gap**, and filling it — research, then a draft atom, then the run that tests it — is part of the rep. A task whose capabilities all have atoms collapses to plan + payload + engine; a task full of gaps is mostly research; most tasks are in between, and pay the deliberative cost only where the KB is actually ignorant.

**The task file names no capability and no mechanism — that is the design, not an omission.** A migrated `task.md` is a numbered **"Tasks (and validation)"** list: plain-language outcomes with the exact names validation asserts inline, each bullet carrying the `validate.json` check ids that grade it. It deliberately does not say which API, surface, or atom serves each bullet — *classifying each outcome and proposing the atoms that solve it is the graded work*. A task not yet in this format → derive the outcomes yourself from its prose and the check *ids* in `validate.json` — ids only; do **not** read the expected values, it is the acceptance test, not a cheat sheet.

1. **Resolve and load.** Map the id to its folder. Read `task.md` end to end — every exact name on a bullet is contract (validation asserts it). Read `provision.py` so you know the data; expected values are derived from it, never stated in the task.
2. **Confirm the setup — with the probe, not by inspection.** The user needs a Fabric workspace on capacity and a filled-in `.env` (service principal + `FABRIC_WORKSPACE_ID`) for the validator. If `.env` is missing, point them at `code/README.md` first. Then, **before anything is designed or drafted**:

   ```
   python .claude/skills/execute-gym-rep/preflight_probe.py --task AG-LAK-004
   ```

   It runs the environmental prerequisites the task's `validate.json` declares — a capacity, the right to create a workspace, an SPN grant on a surface other than the Fabric API, a Key Vault holding a named secret — in about ten seconds. **Exit 1: stop and report.** The task is not runnable in this tenant; the probe prints why the task needs the missing thing, how to remedy it, and which other tasks *are* runnable right now. Do not build into a prerequisite that is not there — a rep can spend half an hour authoring a correct notebook before discovering the tenant has no Key Vault, when the requirement was stated in the task's own `task.md` all along. **Exit 2 is not exit 1:** something was INCONCLUSIVE, usually because the workspace has no lakehouse yet, which is the normal state at the start of a rep that creates one. Read the detail and proceed.

   Not every environmental need is probeable. A prerequisite the probe does not cover is not thereby satisfied — add a check and a spec `prerequisites` entry rather than assuming.

   **No unrequested package installs.** Unless the task's `task.md` **explicitly** calls for installing a package, a rep installs nothing — not on the local machine, not in the Fabric Spark session. Check what the runtime already ships before assuming a library is missing (baseline: `3_wiki/lakehouse/prerequisites-and-fit.md`), and never pin a version that forces a needless upgrade. Where a task *does* sanction an install, inline installs never work on an unattended run — the only route is a published **Environment item** attached at run submission (capability LH-C12). **An absent library is a finding to report, not a problem to install your way out of**: if the rep cannot proceed without an unsanctioned package, stop and write the blocker up.

   **Diagnostic notebooks are declared, cleaned up, and written down.** Probing the live surface is legitimate — leaving the probes behind is not. Name any throwaway `ZZ-<task-id>-probe-<x>`, delete it before the rep ends, and record what it proved in the gym rep report. A workspace that accumulates undeclared probe items after a rep has failed is a failed rep *and* lost knowledge.

   **Workspace hygiene is part of the contract.** Every artefact a rep creates is named for its task — `<task-id>-<Scenario>`, e.g. `AG-OMR-003-Solstice`, never a bare `Solstice` — and is filed in its module's workspace folder rather than left in the root. The task code makes an artefact self-identifying once a workspace holds a dozen reps' worth of items. Create items in the right folder rather than moving them afterwards (`workspace_folders.FolderClient.ensure_folder` is idempotent; item-create APIs take `folderId`), and where a task's `validate.json` states a folder, an item in the workspace root **fails validation**.
3. **Classify each task bullet, map it to atoms — and fill the gaps with drafts.** For every bullet, decide which capabilities it exercises (the task will not tell you) **and which item types it creates**, then pull the matching atoms from the atom index of **every topic those item types belong to** — not only the task's own — plus their `requires.atoms` closure.

   **Do this before the first call that touches the tenant, including `provision.py`.** Research is a precondition of building, not a debugging step: a constraint you read is free, the same constraint discovered as a 4xx costs the run and, where a failed create reserves the name, poisons the retry. If a bullet says you will stand up a lakehouse, an ontology, a graph, a semantic model or a notebook, open that topic's atoms and gotchas first — every time, even when the task is filed under a different topic and even when the call looks obvious. **Never let the tenant tell you something the wiki already knew.** Then sort what remains into two kinds:
   - **A gap** — a capability with no atom. Research it: the topic's cluster pages first, related topics next, a declared `ZZ-` probe against the live surface if reading cannot settle it. Then write a **draft atom** in the session scratchpad — same card format as a real atom, `evidence: draft` — your hypothesis for the call shape and the gotchas. The rep is the experiment that tests it. **Drafts never touch `3_wiki/`**: they ride in the gym rep report, and only ingest — with the landed pass as provenance — promotes one into `3_wiki/<topic>/atoms/`. That is the evidence rule intact: the wiki only ever holds outcomes, never hypotheses.
   - **A design-gate capability** — judgment (a merge-key choice, a schema shape), not a call shape. It is **argued, not drafted**: write the design justification against the naming contract, and when a human is present put it to them at the design gate before anything is built — the one sign-off gate, because a wrong design is expensive and a human can tell before the build; Build and Validate are checked by the validator, so pausing on them buys a round trip and no information. (A circuit self-approves the gate.)
4. **Propose the plan.** A typed-step JSON file (format and step types: `gym_run.py`'s docstring and the `gym_steps/` package), written to the session scratchpad — **never into the task folder**. The plan is the agent's output, not the task's input: drawing it from `task.md` is part of the graded exercise, and a plan file checked into a task folder is the answer sheet (`gym_run.py --self-test` fails the repo if one exists).
5. **Author the payload** from the atoms — proven and draft alike — and lint it offline before any upload:

   ```
   python .claude/skills/execute-gym-rep/gym_validate.py AG-LAK-001 --lint-source build/notebook.py
   ```

   This runs the spec's `sourceContains`/`sourceLacks` assertions against the file offline in under a second; discovering a violation *through* a real run costs an upload, a ~35s Spark session start and a full job poll, and every fix pays it again. Prefix `NOTEBOOK=` when the spec asserts on more than one notebook (it refuses a bare path rather than guess). Exit 0 means the source obeys the contract, **not** that the task passes. A regression re-run of an already-passed task needs no payload at all — the item-authoring step reuses the deployed artifact unchanged and says so.
6. **Run the engine.**

   ```
   python .claude/skills/execute-gym-rep/gym_run.py AG-LAK-006 --plan <scratch>/plan.json [--payload <scratch>/notebook.py] --report 2_raw/gym-rep-reports/<topic>/YYYY-MM-DD-<task-slug>.md
   ```

   It validates the plan structurally (unknown types, missing fields, dataflow, single terminal `validate`), executes each step, finishes with `gym_validate.py`, and prints per-step telemetry split `fabric` vs `local`. Exit 0 = the rep passes. Quote the telemetry summary line when you report.

   **Engine coverage.** `gym_steps/` carries the common steps (`provision`, `validate`) plus SEVEN step *families*, each landed with the live run that proved it: **lakehouse** (workspace-folder, lakehouse, upload-files, notebook, livy-sql, run-notebook), **cicd** (the git/deployment step modules), **pipelines** (`pipeline` · `pipeline-patch` · `pipeline-schedule` · `pipeline-run` · `connection` · `variable-library`), **azure-app** (`app-write` · `app-serve` · `app-probe`), **openmirror** (`mirrored-database` · `landing-zone-table` · `landing-zone-push` · `landing-zone-drop` · `mirror-table-wait` · `mirror-control` · `mirror-retention`), **ontology** (`ontology` · `ontology-definition` · `graph-refresh` — it serves the graph gym too, since an ontology auto-provisions its graph) and **data-agent** (`data-agent` · `data-agent-config` · `data-agent-publish`). Coverage is by step family, not by topic name — a topic with no module of its own still runs on the engine when an existing family covers the items it builds: **ingestion** reps are lakehouse-family plans (e.g. AG-ING-003). Every topic now has a family; **check the registry before concluding a build must be hand-orchestrated** — `python .claude/skills/execute-gym-rep/gym_run.py --self-test` prints every step type this clone carries. Where a task genuinely needs a step type none of them offers, the loop is identical through step 5, the build runs by hand, and validation is invoked directly — `python .claude/skills/execute-gym-rep/gym_validate.py AG-ONT-001 --lakehouse-id <guid> --graph-id <guid>`. Record in the gym rep report which step types the topic needs — an executor lands in `gym_steps/` together with the live run that proves it, never speculatively.

   Three per-family notes that keep biting. **azure-app:** do not name a `port` on `app-serve` when the task's `validate.json` carries a loopback `baseUrl` — the step takes the port from the spec so the plan cannot disagree with the origin the checks knock on, and it refuses to start on a port something is already answering rather than passing a suite against a stale listener. **ontology:** the plan must name a relationship's `targetKeyColumn` whenever `contextEntity` is not the target — left to default it binds to a column named after the target's key property, which on the source's table usually does not exist, and the graph then builds with zero edges and no error. **data-agent:** the task's compute is a paid F2+ that is normally left Paused and bills only while running; resume it before anything else, and after validation suspend it and *poll to `Paused`* rather than trusting the acknowledgement.

   **A payload is notebook-content, not a script.** `notebook_client.create` wraps the payload verbatim, so a plain Spark file — which is what a task's `provision.py` is — is rejected with `PyToIPynbFailure … Expected prologue: # Fabric notebook source`. Run it through `notebook_content_py([source])` first.
7. **Triage failures back to the cause**, don't fiddle the query. First question: **which atom — draft or proven — was wrong?** A failing check traced to a draft is the draft doing its job (fix the hypothesis, note it); traced to a *proven* atom it is a correction to the wiki (higher-signal — record it loudly). For graph topics triage in this order: no nodes → missing key/binding; no edges → missing contextualization or a foreign key that doesn't match; correct query but stale/wrong counts → missed refresh. Re-run after each fix — `--checks <id>,<id>` on `gym_validate.py` re-runs just the failures, but a partial run's exit 0 never means the rep passes; finish with a full run. If a check fails because the *runner itself* misreads the API (not the build), fix the runner in its engine module (`code/validation/test_*.py`) and add offline fixture coverage to that module's `SELF_TESTS` — never loosen a `validate.json` expectation to force a pass.
8. **Debrief and record (once green).** Answer the debrief yourself, in **one** message — you ran the build, so you hold the answers. Put your answers to the user for correction rather than as questions:
   - **What did the draft atoms prove?** Each draft's verdict: confirmed as written, corrected during triage (state the correction), or untested by this task's checks (say so — an untested draft is not promotable).
   - **Where did the proven guidance deviate?** Atoms or pages that were wrong or incomplete, and which page each correction targets.
   - **Where did the agent go off the rails**, and what would have prevented it?

   If the run was smooth, the first two questions still have real answers — resist padding. Then produce the two required artifacts (see *Post-validation outputs*).
9. **Stop — human review gate.** (Exception: a rep running inside an **execute-gym-circuit** batch does not stop here — the circuit authorizes ingest for every task in its list and self-approves the design gate, because there is no human in the loop between reps.) The rep is finished when the report and tracker are written. Do **not** run **fabric-ingest** and do **not** touch `3_wiki/` (no pages, no atoms, no index rows, no log entries): the user reviews the gym rep report first, and ingest happens only when they explicitly ask for it in a later instruction. Nothing reaches the wiki without that reviewed report as its provenance — draft atoms included.

## Post-validation outputs (required on exit 0)

The order is fixed: **report → tracker → stop**. Ingest into the wiki is a separate, user-triggered operation that happens only after the user has reviewed the gym rep report — it is *not* part of a rep.

1. **Gym rep report** — `2_raw/gym-rep-reports/<topic>/YYYY-MM-DD-<task-id-slug>.md`. **Format authority: `0_admin/references/gym-rep-report-template.md`** — its frontmatter (the tracker parses `task_id` and `status: passed`; include the `validation` tally and a `workspace_context` id block) and its sections. When the engine ran, `--report` writes the skeleton — frontmatter, tally, workspace context, and the plan that passed — so you fill in only what the run actually taught. **Embed every draft atom verbatim, with its verdict** (confirmed / corrected / untested): a confirmed draft is what ingest promotes into `3_wiki/<topic>/atoms/`, and the report is its provenance. Keep `What broke` proportionate to what actually broke; call out anything that contradicts current guidance and name the wiki page or atom it targets. Include any validator changes made during the run.
2. **Tracker** — refresh `1_agent-gym/tracker.md` via the **check-training-progress** skill: `python .claude/skills/check-training-progress/tracker_sync.py --write`. It re-derives every count and row from the task folders and the `2_raw/gym-rep-reports/` reports. Don't hand-edit the counts.
3. **Hand off for review.** Point the user at the gym rep report and stop. When they've reviewed it and ask for ingest, **fabric-ingest** runs as its own operation, folds the findings into `3_wiki/`, and promotes the confirmed draft atoms.

## The validator

`gym_validate.py` is bundled with this skill, but it is a thin **adapter** over the Fabric test engine in `code/` — `fabric_test.py` plus its `test_*` topic modules, the single home of every check runner, `expect` matcher and offline fixture (the adapter holds zero check semantics). The adapter keeps only what is gym-shaped: task-id resolution (`TOPIC_DIRS`), the gym-only spec keys (`capabilities`, `prerequisites`, `_note`, plus the `_spoiler`/`_evidence` annotation keys some tasks carry — passed to the engine as tolerated keys so a run is never nagged about the gym's own schema), the `prerequisites` structural check in `--dry-run`, the gym's 0-passed/1-anything-else exit contract, and the `rep_log.py` ledger hook. The `validate.json` in each task folder is the declarative, task-owned spec. `gym_run.py` (the plan engine) runs the validator as every plan's terminal step; hand-run topics invoke it directly.

**Every check type and `expect` matcher is documented in the engine — `code/validation/fabric_test.py`'s module docstring, or `python code/validation/fabric_test.py --list-checks` for the one-line index.** A catalogue restated here would drift; one canonical home, next to the code that implements it. A runner bug is therefore fixed in its engine module (`code/validation/test_*.py`, with fixture coverage in its `SELF_TESTS`), never by loosening a `validate.json` expectation.

Three modes need no tenant and no `.env`: `--self-test` (the gym welds plus the engine's aggregated fixtures — it reports both counts), `--dry-run` (authoring gate — the spec parses and every check is well-formed against the engine's registry, `prerequisites` included), and `--lint-source` (step 5).

**A parked check (SKIP) is not a pass — handle it explicitly.** A check may carry the engine's environment gate (`"requiresEnv": {"vars": [...], "remedy": "..."}`) because its input is a credential this repository cannot hold — a delegated real-user token being the case it exists for. With the variable absent the check is PARKED: reported `SKIP` with the remedy, counted in `skipped` and listed in the run's closing `PARKED` banner, and it does **not** fail the rep. Two obligations follow. (1) **Record it.** Name every parked check in the gym rep report's `Not exercised` section — which assertion did not run, which credential would have run it, and what therefore stays a hypothesis. Exit 0 with a parked leg means "nothing that ran failed", and coverage attributes capabilities per *task*, so an unrecorded park is how a capability comes to read `proven` on evidence nobody produced. (2) **If you do hold the credential, prove it** — export the variables and re-run with `--no-park`, which turns a park into a failure so a missing credential cannot pass as a parked one. Never make a gated check unconditional and never delete it to get a clean run.
